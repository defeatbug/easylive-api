# 评测方法（M6）

本文档定义**每个数字是怎么来的**。论文里引用的任何指标，都应该能用这里的定义与命令复现。

## 1. 四个维度与测量口径

| 维度 | 指标 | 怎么测 | 边界（不包含什么） |
|---|---|---|---|
| 延迟 | 单向延迟 P50/P95 | 自定义 RTP 头扩展 `urn:easylive:send-timestamp` 携带发送时刻（毫秒）；接收端用**同一个进程级时钟**减去它 | **不含**采集、编码、解码、渲染；是"传输 + 服务端转发"的耗时 |
| 延迟 | RTT P50/P95 | 被提名（nominated）候选对的 `currentRoundTripTime` | — |
| 质量 | 抖动、丢包率 | `inbound-rtp` 的 `jitter` / `packetsLost` 差分 | 丢包率按"本窗口丢失 / (丢失+收到)"算，不是累计值 |
| 吞吐 | 上行码率/路 | **发送端自计数**（逐包累加载荷字节） | Pion 的 `GetStats()` **不产出 outbound-rtp**，所以上行只能自己数（这也更准） |
| 吞吐 | 下行码率/路 | `inbound-rtp.bytesReceived` 差分 | 只算载荷+头，不含重传之外的链路开销 |
| 资源 | CPU 占用 % | `/healthz` 的 `cpuSeconds`（`getrusage` 累计值）两次采样差分 ÷ 墙上时间 | 是**整个进程**的 CPU，不是单房间 |
| 资源 | 内存、goroutine | `/healthz` 的 `heapAllocMB` / `goroutines` 峰值 | Go 堆分配量，不等于 RSS |

两个容易测错的点（都踩过）：

1. **RTT 不能取"所有 succeeded 候选对的最大值"**。ICE 会保留多条连通性检查对，其中有些 RTT 高达 90ms+（例如 ICE-TCP 兜底路径受 TCP 延迟 ACK 影响），而真正承载体的是**被提名那一对**（本机 loopback 实测 0.2—0.4ms）。取最大值会让 RTT 虚高约 500 倍。
2. **单向延迟必须用同一个时钟原点**。发送端与接收端如果各用"自己的启动时刻"做基准，差值会带常量偏差甚至为负，表现为"协商成功但一个样本都没有"。

## 2. 工具

```bash
# 服务端（被压测方）
go run .            # 或 docker compose -f deploy/compose.prod.yml up -d

# 压测端（合成客户端：只收发 RTP，不编码/解码）
go run ./cmd/loadtest \
  -ws ws://127.0.0.1:8080/ws \
  -room bench -lanes 4 -duration 30s \
  -video-kbps 800 -audio-kbps 64 -fps 30 -subscribe \
  -out results -tag loopback-4lanes
```

输出：`results/<时间戳>-<tag>/` 下 `lanes.csv`（每路每秒一行）、`server.csv`（服务端每秒一行）、
`summary.json`、`summary.md`。

常用参数：

| 参数 | 说明 |
|---|---|
| `-lanes` | 并发路数；每路发布 1 视频 + 1 音频，并订阅其他人的轨道 |
| `-video-kbps` / `-audio-kbps` | 每路目标码率；`-video-kbps 0` 可只测音频 |
| `-subscribe=false` | 只发布不收（测"广播扇出"与"纯上行"） |
| `-debug` | 打印协商细节：payload type、扩展 ID、extmap、候选对 |
| `-stagger` | 各路的启动间隔（默认 150ms，避免惊群） |

**为什么用合成客户端而不是浏览器**：浏览器的编解码与渲染会先成为瓶颈，测出来的上限是**测试机的能力**；合成客户端只收发 RTP，测的是**服务端的转发与信令开销**。主观画质与端侧耗时必须另用真实浏览器测。

## 3. 实验矩阵

`scripts/matrix.sh` 会依次跑下面这组组合（可用环境变量覆盖），每个组合一个结果目录：

| 变量 | 取值（默认） | 目的 |
|---|---|---|
| 路数 | 2 / 4 / 8 / 12 / 16 | 找单节点容量拐点 |
| 每路视频码率 | 500 / 1500 / 2500 kbps | 验证"只转发"的线性度 |
| 链路 | 直连（默认）/ 强制中继 | 量化 TURN 的代价 |
| 屏幕共享 | 关 / 开（额外一路视频轨） | 验证"容量按视频轨计"的口径 |
| 是否订阅 | 是 / 否 | 区分"发布开销"与"扇出开销" |

```bash
LANES="2 4 8" VIDEO_KBPS="800 1500" ./scripts/matrix.sh
```

公平性要求：

- 对照组（LiveKit）必须**同机型、同码率、同路数、同订阅关系**；建议两种口径各跑一遍并在论文中说明：
  (a) 功能子集对等（只开音视频转发）；(b) 开箱默认配置。
- 每组**重复 ≥ 10 次**，报告 P50 与 P95，保留原始 CSV。
- **压测端与被测服务端分离到两台机器**。同一台机器上跑会让 CPU 数字互相污染——
  下面第 4 节的基线就是同机跑的，因此 CPU 只能当上界看。

## 4. 本机 loopback 基线（不是正式实验数据）

环境：macOS 单机，服务端与压测端**同一台机器**，4 路 × (800 kbps 视频 + 64 kbps 音频) × 15s，全订阅。

| 指标 | P50 | P95 |
|---|---|---|
| RTT | 0.3 ms | 0.4 ms |
| 抖动 | 0.7 ms | 0.9 ms |
| 丢包率 | 0 % | 0 % |
| 单向延迟（传输+转发） | 1.0 ms | 1.0 ms |
| 上行/路 | 863 kbps（目标 863，误差 <0.1%） | — |
| 下行/路 | 1969 kbps（3 路远端 × 656） | — |

服务端：峰值 4 人 / 8 轨道 / 427 goroutine / 堆 19.4 MB / **CPU 平均 15%、峰值 45.6%**。

> ⚠️ CPU 这一行**不能作为结论**：压测进程与服务端抢同一台机器的 CPU。
> 正式实验必须把压测端放到另一台机器（或至少另一台容器并限制 CPU）。

## 5. 与 LiveKit 对比的操作步骤

1. 同一台服务器上准备两份编排（本项目 `deploy/compose.prod.yml`；LiveKit 用其官方 compose），**逐个启动、不要同时跑**。
2. 固定实验条件：分辨率/码率/帧率、路数、订阅关系、是否屏幕共享、压测时长、重复次数。
3. 两边的压测端都用 `cmd/loadtest`（同一份客户端消除"客户端差异"这一变量；LiveKit 也提供标准 WebRTC 接口）。
4. 采集同一组指标：`/healthz` 换成 LiveKit 的 Prometheus 指标即可，CPU/内存用 `docker stats --no-stream`。
5. 结果表至少包含：路数 → 单向延迟 P50/P95、丢包率、每路码率、服务端 CPU、内存。

## 6. 本机无法覆盖、必须到服务器上做的部分

- 真实公网路径与 NAT 穿透（本机只有 loopback）；
- **强制中继**：把 `TURN_URLS` 只留 `?transport=udp` 并封掉 7881/udp，用界面「指标」面板确认 `candidateType=relay`，再对比 RTT/码率；
- LiveKit 同条件对照（需要能跑它的容器）；
- 与数据库相关的链路（迁移执行、指标落库、聚合查询）——见 `deploy/README.md` 的验收清单。
